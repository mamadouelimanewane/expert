Périmètre et méthode

Les tests ont été exécutés contre l'instance locale connectée à la base MongoDB Atlas de production, avec une session staff authentifiée. Les appels API ont été émis depuis le navigateur (mêmes cookies, même middleware que l'utilisateur final) ; les écrans ont été rendus en 375 px, 768 px et 1 280 px. Toutes les données de test portaient le préfixe ZZ-TEST-CERTIF et ont été supprimées à la fin (client, 2 missions, 18 écritures, 4 documents, factures, lettre, réunions, dépenses, webhooks, clé API). Aucun paiement Mobile Money réel n'a été déclenché.

Constats corrigés

Numérotés dans l'ordre de découverte. Chaque correctif a été re-testé par l'appel ou l'écran qui l'avait révélé.

C-01bloquant
Bloquant démo

Aucune fiche client, aucune modification possible

Le « CRM 360° » ne permettait ni d'ouvrir un dossier ni de corriger un NINEA ou une adresse ; /api/clients/[id] n'acceptait que GET (PATCH/DELETE → 405).

Fiche /clients/[id] (identité modifiable, indicateurs, missions, factures, temps, documents, lettres, archivage) et API PATCH/DELETE avec validation et journal d'audit.

C-02bloquant
Bloquant démo

Portail client inaccessible depuis l'interface

Le jeton portail n'est jamais renvoyé par l'API (choix de sécurité correct), mais la liste des clients conditionnait le bouton « copier le lien » à sa présence : il ne s'affichait jamais.

Route /api/clients/[id]/portal-link réservée aux rôles écriture : afficher, régénérer, révoquer — chaque consultation journalisée. Vérifié : ancien jeton → 404 après régénération, jeton révoqué → 404.

C-03bloquant
Bloquant démo

Missions figées en brouillon

Le kanban était en lecture seule ; aucune route ne permettait de faire avancer une mission (PATCH → 405). Les statuts « En cours », « À réviser », « Terminée » n'étaient jamais atteints.

API /api/missions/[id] avec transitions contrôlées (refus 409 explicite), fiche /missions/[id], menu d'avancement sur chaque carte du kanban.

C-04majeur
Majeur

Écritures validées absentes du bilan

La validation depuis « Abonnés TPE » passe une écriture en APPROVED ; le déversement en production ne prenait que PENDING. Une écriture validée par l'expert n'entrait donc jamais dans le bilan, le résultat ni le FEC.

Déversement de PENDING et APPROVED. Re-test : 18 écritures déversées, bilan équilibré.

C-05majeur
Majeur

Documents figés en « PROCESSING »

L'OCR serveur ne rendait jamais la main : le worker Tesseract, bundlé par Turbopack, ne retrouvait plus son chemin. En Node pur, la même image est reconnue en 5 s à 95 %.

tesseract.js et sharp externalisés (serverExternalPackages), délai maximal 45 s (statut ERROR au lieu d'un blocage), maxDuration 60 s, cache des langues dans /tmp (seul répertoire inscriptible sur Vercel).

C-06sécurité
Sécurité

Webhook vers une adresse interne accepté (SSRF)

Un compte staff pouvait enregistrer http://localhost/… ou une IP privée comme destination de webhook et faire sonder le réseau interne par le serveur.

Seules les URL https:// vers un hôte public sont acceptées ; identifiants dans l'URL refusés.

C-07majeur
Intégrité

Montants négatifs ou nuls acceptés à l'import

Une ligne « −5 » était importée en valeur absolue sans avertissement ; une ligne à 0 créait deux écritures vides.

Rejet explicite avec le numéro de ligne et le motif ; aucune écriture n'est enregistrée si une ligne est invalide.

C-08robustesse
Robustesse

Cinq routes répondaient 500 « Erreur serveur » à une saisie invalide

Alertes fraude (sévérité, statut), dépenses (catégorie), réunions (type, fin avant début), relances sans facture, paie sans salarié — cette dernière créant au passage une période de paie « VALIDATED » vide.

Validation des énumérations avec message listant les valeurs admises (400), contrôle de cohérence des dates, vérification des salariés avant toute écriture.

C-09ergonomie
Ergonomie

Raccourcis mobiles sans action, overlay vocal simulé, alert() natifs

« Scanner facture » et « Nouvelle mission » du menu flottant ne faisaient rien ; « Note vocale IA » jouait une transcription scriptée avec des chiffres inventés ; 13 retours utilisateur passaient par alert().

Liens réels, overlay supprimé au profit de /nexus-go (vraie reconnaissance vocale), système de notifications, sidebar dédoublonnée (44 destinations uniques), fiches reliées.

C-10ergonomie
Ergonomie

Application non utilisable sur téléphone

Grilles à 3-7 colonnes forcées, chiffres en 72 px, barres d'onglets tronquées, boutons flottants recouvrant le contenu, erreur d'hydratation sur le hub.

Filet CSS mobile, barres d'onglets défilantes, formatage des heures en fuseau fixe ; 30 écrans vérifiés sans débordement à 375 px.

C-11chaîne
Chaîne de livraison

Intégration continue en échec depuis le 1er septembre, APK jamais produit

Conflit de dépendances (nodemailer 9 / next-auth), action GitHub disparue, Java 17 pour Capacitor 8, URL de production obsolète dans la configuration Android.

CI verte (typecheck, lint, 388 tests, build) et APK app-debug.apk généré à chaque push.

Prérequis avant la démonstration

  • Ajouter WHATSAPP_APP_SECRET dans Vercel et redéployerSans lui, chaque message WhatsApp entrant est rejeté (L1). Vérifier ensuite avec scripts/ de vérification du token.
  • Confirmer que expert-pi.vercel.app sert le commit 534e735Le déploiement Vercel se déclenche à chaque push ; ouvrir /clients, cliquer un dossier : la fiche doit s'afficher.
  • Préparer un jeu de données de démo cohérentLa base contient encore des clients de test hétérogènes (« Chez Awa Test Verification », factures au client « N/A »). Créer 3 dossiers propres avec écritures, factures et lettres — ou utiliser npm run seed:demo sur une base dédiée.
  • Écrire le scénario en évitant L3, L4, L6Parcours conseillé : hub → fiche client → mission (démarrer, terminer) → scan d'une facture (OCR) → import d'écritures → validation → bilan / liasse → export FEC → facture d'honoraires → portail client.
  • Tourner les mots de passe de démo exposés dans l'historique gitnpm run rotate:passwords si ce n'est pas déjà fait (voir L9).
